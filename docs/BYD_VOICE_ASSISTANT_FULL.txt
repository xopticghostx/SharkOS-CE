BYD SHARK 6 VOICE ASSISTANT: WHAT WE FOUND, HOW TO USE IT, AND EVERY COMMAND
Written 21 Nov 2026 for SharkOS-CE. Car: BYD Shark 6, firmware SOC_260811_S.
Source of everything below: BYD voice assistant app com.byd.vrassistant (BydVoice.apk,
versionName S.10.1.7, versionCode 177, SHA-256 ef416592b41bbe19a891f18f77e64a41a9d396279d238368485b946d278aa4c2),
pulled from /product/app/BydVoice/ and read with dexdump, plus live tests on the car.
NOTICE: this file is unofficial community research and is not affiliated with or endorsed by BYD. The phrase, request and intent
lists in sections 7 to 9 are extracted from BYD's own voice assistant app and remain BYD's; they are included for interoperability
research only. Changing car settings is at your own risk: change one thing at a time while parked.
Status words used: VERIFIED = tried on the car and checked against BYD's own screen or a read-back.
DECODED = read from BYD's code only, NOT tried on the car.

==============================================================================
1. THE SHORT VERSION
==============================================================================

- The voice assistant makes the same android.hardware.bydauto.* calls that SharkOS-CE makes. So the
  assistant's own code is a reliable list of "what the car expects" for each spoken action, including
  the exact write VALUES. Reading it gave us the window write that nothing else had.
- We could NOT send a spoken command from adb. Audio played from the car's own speakers is not heard by
  the assistant (its overlay just kept cycling hints), and the app has no text-input entry point.
  So the working method is: read the assistant's code to learn the call, then fire that same call
  ourselves (our ADB test hook / codes file) and check the result on BYD's own screen.
- Found and used today: window open/close (VERIFIED on the front-left window), recirculate encoding
  (VERIFIED, and it exposed a bug in our own app), Bluetooth, screen brightness, rear window lock,
  and the full list of requests and intents the engine understands (sections 8 and 9).


==============================================================================
2. CALLS THE BYD VOICE ASSISTANT MAKES (SPOKEN ACTION -> CAR CALL)
==============================================================================

1. Open / close a window
   Call:   bodywork.BYDAutoBodyworkDevice.setWindowControlState(int[4])
   Array index 0 = front left, 1 = front right, 2 = rear left, 3 = rear right. Value 0 = leave that window alone.
   Value 1 = open, 2 = close, 4 = half, 5 = small gap. The assistant picks the value from the percentage you ask for:
   more than 90 -> 1, under 5 -> 2, 40 to 60 -> 4, 5 to 20 -> 5, anything else is refused ("UNSUPPORTED").
   It refuses while the window lock or child lock is on. It reads positions with getWindowState(1..4).
   Status: VERIFIED on the front-left window: [1,0,0,0] opened it, [2,0,0,0] closed it (open % read 9, 88, 97 on the way). The other windows and codes 4 and 5 are DECODED only. The Shark 6 has no adjustable rear windows.

2. Read a window position
   Call:   caradapter body.getWindowOpenPercentLeftFront / RightFront (and LeftRear / RightRear)
   0 to 100 percent open. It reads 0 when closed and 97 to 98 when fully open.
   Status: VERIFIED

3. Recirculate on / off
   Call:   ac.BYDAutoAcDevice.setAcCycleMode(1, x)  (BYD's own climate screen sends setAcCycleMode(0, x))
   x = 1 means recirculate, x = 0 means fresh air. The assistant reads the current mode with getAcCycleMode() first.
   Read side (caradapter hvac getAcCycleMode): 2 = recirculate, 1 = fresh air.
   Status: VERIFIED with the (0, x) form against BYD's climate screen. The (1, x) form is as read from the code and was not exercised.

4. Rear window lock
   Call:   doorlock.BYDAutoDoorLockDevice.setRearWindowLock(v);  read getDoorLockStatus(6)
   Write v = 2 -> the read shows 1. Write v = 1 -> the read shows 2. (The read is the inverse of the write.)
   In the assistant's code a read of 1 means "locked", so write 2 = lock and write 1 = unlock.
   Status: The write/read relationship is VERIFIED on the car; which value means "locked" comes from BYD's code. No control was built (no rear windows).

5. Bluetooth on / off
   Call:   android.bluetooth.BluetoothAdapter.enable() / disable()
   Plain Android.
   Status: VERIFIED from the SharkOS-CE Bluetooth tile (settings value 1 -> 0 -> 1).

6. Screen brightness
   Call:   Settings.System "screen_brightness" (0 to 255) for the centre screen; the instrument cluster uses bydauto.instrument.BYDAutoInstrumentDevice.setInstrumentBrightness(int)
   The assistant converts a 0-100 request to 0-255 for the centre screen.
   Status: The setting VERIFIED to change (169 -> 130 -> 169 and 169 -> 139 -> 169, written with: settings put system screen_brightness N through the unit's own adb). That the panel visibly dims is not yet confirmed by eye.

7. Mobile data
   Call:   TelephonyManager.setDataEnabled(boolean) by reflection; read with getDataEnabled
   Needs a privileged phone permission.
   Status: NOT usable by us. "svc data" and "cmd phone data" changed nothing here (the connection is the T-Box network, type Tbox).

8. Door lock
   Call:   doorlock.BYDAutoDoorLockDevice.setDoorLockStatus(a, b)
   Values not decoded.
   Status: DECODED call name only.

9. Climate
   Call:   ac.BYDAutoAcDevice: setAcControlMode(II), setRearAcControlMode(II), setAcCompressorMode(II), setAcTemperatureControlMode(II), setAcWindMode(II), setRearAcWindMode(II), setAcMaxCoolingState(I), setAcDefrostState(III), stop(I), stopRearAc(I), setQuickCleanAirState(I)
   Values not decoded.
   Status: DECODED call names only.

10. Seat heat, seat vent, steering wheel heat
   Call:   setting.BYDAutoSettingDevice: setSeatHeatingState(II), setSeatVentilatingState(II), setSteeringWheelHeatingState(I)
   Values not decoded.
   Status: DECODED call names only.

11. Air purifier
   Call:   pm2p5.BYDAutoPM2p5Device: setPM2p5CheckState(I), setPM2p5DualChannelDetectState(I), setPM2p5AnionDetectState(I)
   Values not decoded.
   Status: DECODED call names only.

12. HUD on / off
   Call:   setting.BYDAutoSettingDevice.setHudState(I)
   Value not decoded.
   Status: DECODED call name only.

13. Rotate screen
   Call:   setting.BYDAutoSettingDevice.setScreenRotation(I)
   1 = landscape, 2 = portrait.
   Status: VERIFIED earlier (SharkOS-CE v0.6.766).

14. Fragrance level
   Call:   fragrance.BYDAutoFragranceDevice.setFragranceConcentration(I)
   Value not decoded.
   Status: DECODED call name only.

15. Reading light
   Call:   setting.BYDAutoSettingDevice.setInsideLightDoorState(I)
   true -> 2, false -> 1.
   Status: DECODED only.

16. Power source / drive mode
   Call:   energy.BYDAutoEnergyDevice.setOperationMode(I)
   Value not decoded.
   Status: DECODED call name only.

17. Rear tray (the ute's tailgate; BYD's code calls it the "trunk" or "back door")
   Call:   setting.BYDAutoSettingDevice.voiceCtlBackDoor(int)
   Value:  open percentage 0 (close) -> 3, anything above 0 (open) -> 1. There is no partial opening in this call.
   Read:   bodywork.BYDAutoBodyworkDevice.getBackDoorCurState(): as best read from the code, 1 or 3 is reported as 100 % open and any other value as 0 %.
   Status: DECODED only, NOT tried on the car. Opening the tray moves a heavy panel: do not test without someone at the car
           and the area behind the car clear.

18. Tub light (BYD's "trunk light")
   Call:   none. The assistant's controlTrunkLight handler just answers "UNSUPPORTED" on this variant.
   The Shark 6 tub light is already controlled by SharkOS-CE as the Bed Light tile (signal body.cargoLight).
   Status: nothing to decode.

NOT ON THE SHARK 6 (checked 21 Nov 2026): it is a ute with no sunroof and no boot/trunk. The voice engine still lists
sunroof and trunk requests (CONTROL_SUNROOF, GET_SUNROOF_STATE, SET_TRUNK_STATE, GET_TRUNK_STATE) because it is shared across
BYD models; on this car the trunk requests act on the rear tray, and the sunroof ones do nothing useful. The Shark 6 also has
no adjustable rear windows. It does have rear power points; the voice assistant has no handler for them (they belong to the
V2L / charging side, see CHANGELOG v0.6.774 for the read-only V2L probes).

Handlers still to read (names only so far): blinds/sunshade (probably unused here), interior light colour and
brightness, drive mode, road mode, nap mode, camera record/photo, ADAS, child lock, engine sound,
wing-mirror heating, hotspot, Wi-Fi. They are in com.byd.vrassistant.conversation.*Helper classes.

==============================================================================
3. HOW TO READ THE WRITE VALUE FOR ANY VOICE COMMAND
==============================================================================

Needs: the car on adb over Wi-Fi, Android build-tools (dexdump), and a text editor. No root needed.

 1. Pull the app (read-only):
      adb -s <car-ip>:5555 pull /product/app/BydVoice/BydVoice.apk
      (Git Bash: set MSYS_NO_PATHCONV=1 first, or the path gets rewritten.)
 2. Unzip classes*.dex and disassemble each one:
      dexdump -d classes2.dex > c2.txt        (build-tools\36.0.0\dexdump.exe; the file is ~1.8 million lines)
 3. Find the helper for the action. The useful classes are in com.byd.vrassistant.conversation:
      BydSdkHelper (window state, window lock, cellular data, child lock)
      VehicleBasicHelper (setWindowState, controlWindowLock, controlChildLock)
      HvacSetStateHelper / HvacHelper / Hvac*Helper (climate, seat heat/vent, defrost)
      VehicleScreenHelper (brightness), VehicleLampHelper (interior light), VehicleSettingsHelper (Bluetooth, hotspot)
 4. In the dump, search for "] com.byd.vrassistant.conversation.<Class>.<method>:" and read until the next
    "] " method header. The lines that matter are:
      const/4 vN, #int X    -> a literal value
      aput vV, vA, vI       -> puts a value into an int[] (this is how the window array is built)
      invoke-virtual {..}, Landroid/hardware/bydauto/<dev>/<Class>;.<method>:(sig)  -> the car call
    Walk back from the invoke to see what value each branch loads (for example 'percent > 90 -> 1').
 4a. Request names (what a spoken request is called inside the engine) are the field names of
    cerence/ark/assistant/controller/domain/<domain>/<Domain>RequestsEnum (section 8).
 5. Remember a "read" that the assistant uses is often the inverse of its write (rear window lock), and
    the first argument can differ from BYD's own app (recirculate uses 1 here, 0 in the climate app).
    Always confirm on the car (section 5), never trust the decoded value alone.


==============================================================================
4. HOW TO FIRE A DECODED WRITE ON THE CAR (SAFELY)
==============================================================================

SharkOS-CE v0.6.780 and later accept an int[] argument in shark6_codes.json as a nested array:
      "args": [[1, 0, 0, 0]]          -> setWindowControlState(new int[]{1,0,0,0})
A temporary override file is the safe way to try a new call without rebuilding:
 1. Copy shark6_codes.json, add a signal with "labels" and "writeLabels" (see window.ctl.frontLeft in the
    shipped file for a complete example), save it as the override.
 2. adb push it to /sdcard/shark6_codes.json, then on the car:
      cp /sdcard/shark6_codes.json /storage/emulated/0/Android/data/com.sharkhome.launcher/files/shark6_codes.json
      chmod 644 that file
 3. Reload and test with the built-in hook (results log to tag SharkCar):
      adb shell am broadcast -a com.sharkhome.launcher.ADB_TEST -n com.sharkhome.launcher/.car.AdbTestReceiver --es cmd reload
      ... --es cmd read --es keys "your.signal"
      ... --es cmd verify --es keys "your.signal" --es target on --ei waitMs 8000
    verify reads the value, writes the target, reads it back, then writes the original back.
 4. Delete the override file when done and send cmd=reload again (log shows origin=built-in).
Before changing any car setting: say what you are about to change, change one thing, and put it back.
Windows are slow (about 5 s to open), so use a long waitMs or poll the read yourself; the generic confirm
reports "not confirmed" for slow moves even when they worked. Never test a window with people or
objects in its path.


==============================================================================
5. TEST STEP: CHECK THE ACTION IS CORRECT WHEN IT IS EXPOSED TO VOICE
==============================================================================

Use this whenever an action in SharkOS-CE (or any new voice integration) is meant to match what the
BYD assistant does. The point is that "the read-back matched our own table" is NOT proof; on 20 Nov the
recirculate tile shipped inverted even though every read-back said confirmed=true.

 For each action:
  [ ] 1. Find the assistant's call for the phrase (section 3) and write down: device, method, argument values.
  [ ] 2. Find the read the assistant uses for the same state and write down what each value means.
  [ ] 3. Record the starting state (read it) so you can put it back.
  [ ] 4. Fire OUR write (not the voice one) and read the value back; allow for slow reports (3-5 s, windows ~8 s).
  [ ] 5. Compare with the OUTSIDE truth, not with our own labels: BYD's own screen (zoom in on the icon),
         or the physical result. Example: BYD climate screen shows a loop arrow inside the car for recirculate
         and an arrow entering from outside for fresh air.
  [ ] 6. Confirm the write and read directions agree with the assistant's code (is 1 on or off? is the read the
         inverse of the write?). Rear window lock reads the inverse of what you write.
  [ ] 7. Put the car back to the starting state and read it again to prove it.
  [ ] 8. If a voice command can be tested for real (someone speaks, or the assistant's overlay shows the
         recognised text), say the phrase and check the car lands in the same state as step 4.
  [ ] 9. Write the verified encoding into shark6_codes.json (_note) and BYD_SHARK6_REFERENCE.md. Mark anything
         not tried as UNVERIFIED.

 Known-good checks so far (21 Nov 2026):
   recirculate  write (0,1)/(1,1) = recirculate, (0,0)/(1,0) = fresh; read 2 = recirculate, 1 = fresh. BYD climate screen agrees.
   window       [1,0,0,0] opens front left, [2,0,0,0] closes it; open % read goes 0 -> 9 -> 88 -> 97.
   rear window lock  write 2 reads back 1; write 1 reads back 2.


==============================================================================
6. TALKING TO THE ASSISTANT FROM ADB (WHAT WORKS, WHAT DOES NOT)
==============================================================================

WORKS
 - Start it listening without the wake word:
      adb shell am broadcast --receiver-foreground -a com.intent.action.StartVoice_From_Launcher -n com.byd.vrassistant/.receiver.HardKeyReceiver
   (without -n and --receiver-foreground Android blocks it as "background execution".)
 - Its overlay bar (top right of the screen) shows what it thinks it heard, so a screenshot shows the transcript.
 - It logs at warning level under tags NEU_* (NEU_VoiceAssistantManager, NEU_CustomSystemDomain, ...). Its
   info/debug lines (recognised text, results) are hidden on this head unit.
 - SharkOS-CE v0.6.779 has  --es cmd play --es file name.wav  in the ADB hook to play a sound file from the
   app's files folder.
DOES NOT WORK
 - Playing a speech WAV from the car's own speakers: the assistant did not hear it (its overlay only cycled
   hints, nothing changed). Probably echo cancellation; not proven.
 - No text-input hook on the device. The Cerence ARK events (PTT, CANCEL_DIALOG, ...) carry no text.
 - BYD's test harness receiver AutoRunReceiver (actions bydvoice.broadcast.autobatch.start/pcm/stop, extras
   filename and data_path) accepts broadcasts from adb but needs prepared recordings and a JSON dialog list and
   restarts the engine each call; the format was not worked out. After a probe the assistant recovered in
   about 5 s ("start Assistant success" in the log).
NOTED, NOT USED
 - The engine's cloud config (data_vr-BASE asr_eng-USA one_cloud_config.json) lists a TextQueryService on BYD's
   Cerence One Cloud (gRPC, OAuth). That would accept text, but it needs BYD's credentials, so we did not touch it.
 - The wake word was not found in the logs or resources (the data pack is "data_eng-USA").

9. EVERY COMMAND TYPE THE ENGINE RECOGNISES (INTENT NAMES)
==============================================================================
From data_vr-BASE/asr_common/config/intent_mapping_domain_config.json: 2186 intents in 39 domains.
Intent names are the internal names of what the engine can understand; the wording you say is free-form
(the language understanding runs on the engine and BYD's cloud), so use these as "what is possible",
